## 三、关键架构决策

### 3.1 重构范围确认

在规范化 Config 过程中，确认以下模块需纳入本轮重构序列：

1. **宝石模块** — UI/交互/数据混杂，`GameObject.Find` 滥用，跨场景数据传递使用字符串列表
2. **装置模块** — 运行时间逻辑与 Manager 强耦合
3. **发射/子弹模块** — 子弹按「发射者」分类导致逻辑重复，需改为按「子弹种类」分类
4. **存档系统** — 从零建设三层数据流转架构

### 3.2 架构原则确立

- **单一职责**：每个 Manager 只处理一类业务逻辑
- **依赖倒置**：UI 层依赖交互层，交互层依赖数据层，数据层对接 SaveManager，层级单向向下
- **统一入口**：所有配置通过 `GameConfig` 读取，所有持久化通过 `SaveManager` 写入
- **策略组合**：宝石/子弹/敌人的能力由独立策略组合而成，策略之间互不知晓

### 3.3 模块解耦方向

识别出祖传代码存在以下耦合链路，需逐步切断：

```
KuManager ←→ Inventory
    ↓
EquipmentManagerInBag ←→ Inventory
    ↓
LevelController ←→ KuManager + EquipmentManagerInBag
```

**改进方案**：引入中介者或事件系统，减少 Manager 之间的直接引用。

## 六、本周思考与复盘

### 6.1 祖传代码核心问题分类

| 问题类型 | 具体表现 |
|----------|----------|
| **职责边界模糊** | UI 脚本（`Slot`）同时处理显示、数据修改、装备逻辑、UI 查找 |
| **单例滥用** | 多个 Manager 手动调用 `Awake()` 补救初始化顺序，幽灵单例频发 |
| **跨场景传参原始** | 使用字符串列表（`Ku.nameList`）传递数据，无类型安全 |
| **脚本粒度过细** | 功能零散，甚至有脚本专门负责跳转到某个特定场景（如 `Back.ToSellect()`） |
| **分类维度错误** | 子弹按「谁发射的」分类，而非按「子弹种类」分类，导致逻辑重复 |

### 6.2 核心教训

> **不能按场景或触发者划分脚本职责，耦合性太差且不可复用。**  
> 根源是早期能力不足，功能粒度过细，缺乏抽象意识。

**后续开发应遵循的原则：**

- **单例模式不是万能药** — 控制使用频率与范围，统一初始化流程
- **按「职责」划分，而非按「场景」或「触发者」** — 一个脚本只做一件事，但要确保那件事有复用价值
- **数据与逻辑分离** — UI 不持有数据，Manager 不持有 UI 引用
- **配置数据资产化** — 使用 ScriptableObject 作为数据容器，逻辑代码只读不写

### 6.3 技术选型预研结论

- 存档：JSON 序列化 + 三层数据分离（跨存档/单局/战斗）
- 能力系统：策略模式（宝石/子弹）+ 状态机（敌人）
- 对象管理：引入对象池（EnemyPool）减少 GC 压力
- 场景管理：按功能拆分独立场景，通过 `GameManager` 统一调度加载
